# Contributing

Thanks for taking the time. This is a small plugin with a narrow purpose, so the
bar for a change is mostly: does it keep the table usable for someone who cannot
see it?

## Ground rules

- **Accessibility is the feature.** A change that makes the visual result nicer
  while weakening the semantics will be declined. If you are unsure, add the case
  to `tests/test-cases.md` with the screen reader output you observed.
- **No JavaScript on the front end.** Ever. The transformation is PHP and CSS.
  The build produces an editor script and a stylesheet, nothing that runs for a
  visitor.
- **No outbound request, no telemetry, no external asset, no database option.**
- **Nothing is written into saved block markup.** See the section on block
  validation in `README.md` before touching the editor script.
- **Bail out rather than guess.** When a structure cannot be labelled honestly,
  the correct behaviour is to leave it alone, not to approximate.

## Getting set up

```bash
git clone git@github.com:Fyrins/tablefold.git
cd tablefold
composer install          # linters
npm ci && npm run build   # editor script and stylesheet
```

`build/` is not committed and the plugin enqueues from it, so the build step is
required before the plugin does anything. Use `npm start` for watch mode.

Symlink the folder into a WordPress install running 6.7 or later.

## Before opening a pull request

```bash
composer lint       # PHPCS
npm run lint:js     # ESLint
npm run lint:css    # stylelint
npm run build       # the package ships build/, so it must be current
```

All three linters must be clean, and the build must be up to date: `build/` is
what ships, and a stale build publishes code nobody reviewed.

Note that `npm run format` reaches beyond `src/`. `.prettierignore` keeps it out
of the workflows and the Markdown, whose indentation follows `.editorconfig`. Then run [Plugin Check](https://wordpress.org/plugins/plugin-check/)
against the plugin from the WordPress admin, with the "Plugin Repo" checks
enabled. It must report no error and no warning.

If your change affects how a table is parsed or rendered, add the corresponding
row to `tests/test-cases.md`, including what NVDA and VoiceOver are expected to
announce.

## Translations

Strings are translated just in time; the plugin calls no `load_plugin_textdomain()`.
Translations are contributed on [translate.wordpress.org](https://translate.wordpress.org/)
and delivered as language packs, so the repository ships no `.po`, `.mo` or `.json`
file, only the template.

Regenerate the template after changing any string:

```bash
wp i18n make-pot . languages/tablefold.pot --slug=tablefold --domain=tablefold --exclude=vendor,node_modules,tests,build
```

Never put a variable or a concatenation inside a translation function, and always
put a `/* translators: */` comment above a string carrying a placeholder.

## Releasing

Only a maintainer can do this. The version number lives in three places and the
deploy workflow refuses to publish when they disagree:

1. the `Version` header of `tablefold.php`;
2. the `Stable tag` of `readme.txt`;
3. the Git tag.

Steps:

```bash
# 1. Bump the version in tablefold.php, readme.txt and the TABLEFOLD_VERSION constant.
# 2. Add the release section to CHANGELOG.md and to the Changelog of readme.txt.
# 3. Commit, then tag.
git tag -a v1.0.1 -m "Release 1.0.1"
git push origin main --tags
```

Pushing a `v*` tag triggers `.github/workflows/deploy.yml`, which checks the three
version numbers agree and then publishes to the wordpress.org SVN repository with
[`10up/action-wordpress-plugin-deploy`](https://github.com/10up/action-wordpress-plugin-deploy).

### Repository secrets

The deploy workflow needs two secrets, created by hand in
**Settings → Secrets and variables → Actions** of the GitHub repository. They are
never generated by any script in this repository.

| Secret | Value |
| --- | --- |
| `SVN_USERNAME` | The wordpress.org account username that owns the plugin |
| `SVN_PASSWORD` | That account's wordpress.org password |

Use a dedicated account if you can, and enable two-factor authentication on it.
If the password is rotated, update the secret before the next tag.

### Screenshots and banners

Assets shown on the plugin page do not live in the plugin folder. They go in the
SVN `assets/` directory, which the deploy action publishes from a local
`.wordpress-org/` folder. File names are fixed by wordpress.org:

- `screenshot-1.png` … `screenshot-4.png`, in the order of the `== Screenshots ==`
  captions in `readme.txt`;
- `banner-772x250.png` and `banner-1544x500.png`;
- `icon-128x128.png` and `icon-256x256.png`.

### First submission

A new plugin is submitted once, manually, at
<https://wordpress.org/plugins/developers/add/>. The review is done by a human and
takes a while. Nothing is pushed to SVN until the plugin is approved and the SVN
repository has been created; only then does the tag-based workflow become useful.
